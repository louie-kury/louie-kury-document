## 목적과 범위

일반 회원가입에 사용할 이메일 인증번호 발송·확인 및 가입 증명 발급을 구현한다. 회원가입 전체 API, 소셜 인증 세부 정책, 이메일 변경, 계정 복구, 프론트엔드와 MongoDB 프로필 생성은 이번 범위에서 제외한다. 실제 가입 시 증명을 소비하는 연동은 후속 가입 API에서 처리하며, 증명 발급만으로 가입이 완료되었다고 보지 않는다.

## 제안하는 동작과 선택

1. 이메일 형식과 목적을 확인하고, 중복 이메일·발송 제한을 원자적으로 검사한다. 보안 난수로 6자리 번호를 만들고 이전 번호를 무효화하며 메일 발송을 요청한다. 발송 실패는 성공으로 반환하지 않는다.
2. 인증 ID와 코드를 확인한다. 만료·실패 횟수·동시 요청을 원자적으로 처리하고 성공 시 이메일·SIGNUP 목적에 묶인 10분짜리 일회성 증명을 돌려준다. 응답과 저장의 만료 시각을 일치시킨다.
3. Redis 원자 연산과 메일 발송 포트를 사용하고 Brevo 트랜잭션 메일 API를 연결한다. 실제 발송에는 인증된 발신 주소와 키가 필요하다.

### 이번 대화에서 정한 사항과 현재 구현

- 이메일은 앞뒤 공백을 제거하고 ASCII만 허용한다. 중복·제한 비교는 이메일 전체의 대소문자를 무시하고, 실제 발송 주소는 입력한 대소문자를 보존한다. `+`와 `.`은 임의로 제거하지 않는다.
- 사용자가 Brevo를 발송 수단으로 선택하고, IP별 발송 제한은 시간당 100회로 정했다. 기존 이메일당 60초 재발송·시간당 5회 제한은 유지한다.
- 서비스는 전달 헤더를 임의 신뢰하지 않고 연결 원격 IP를 사용한다. 프록시 뒤에서는 신뢰할 수 있는 프록시 설정이 없다면 여러 사용자가 같은 IP로 집계될 수 있다.
- 발송 실패 또는 결과가 불명확해도 발송 횟수를 차감하고 이전 번호를 무효로 유지하는 방식은 이번 구현의 보수적 처리 방안이다. 사용자 선택으로 기록하지 않는다.
- 발신 도메인·주소와 키가 아직 준비되지 않아 실제 Brevo 수신은 미검증이다. 가입용 증명 소비, 확인 API 및 가입 API 연동은 이번 발송 단계에서 구현하지 않는다.

### 구현 전 해결할 충돌과 확인

- 공통 API 초안은 이메일 로컬 부분의 대소문자를 구분한다. 이는 사용자 결정인 전체 대소문자 비구분 및 ASCII 제한과 다르므로 공통 API 문서 동기화가 필요하다. 기존 DB `utf8mb4_0900_ai_ci`의 악센트 비구분은 비ASCII 입력을 거절하는 이번 발송 정책과 구분해 기록한다.
- PRD는 이메일 등 개인정보 암호화를 요구하지만 #3 계획서는 사용자가 현재 ERD 컬럼 형식 저장을 지정하여 공통 문서 변경을 보류했다고 기록한다. 실제 결정 범위와 인증용 저장·조회 영향을 확인한다.
- 이메일 누적 실패 제한의 수치·해제 기준은 확인 API 구현 전에 정해야 한다. 발송 공급자와 IP별 제한은 위 사용자 결정을 따른다. 가입 API의 증명 소비·복구 및 소셜 정책은 후속 범위다.

## 진행 순서와 변경 파일

1. 사람이 충돌과 범위를 확인하고 이 계획을 승인한다.
2. 승인된 계획으로 메인이 이슈를 작성하고 사람의 이슈 승인을 기다린다.
3. 이슈 승인 후 최신 대상 브랜치 및 작업 트리 상태를 확인하고 Git 컨벤션에 맞춰 브랜치를 만든다.
4. implementer는 auth-service의 `account` 또는 별도 인증 기능 패키지에 발송·확인 유스케이스, 웹 요청·응답, 저장·발송 포트 및 Redis·메일 어댑터를 추가한다. `build.gradle`, `application.yaml`, 기존 웹 오류 매핑과 README 설정 안내를 필요한 만큼 변경한다. 실제 파일명과 의존성 버전은 최신 코드 및 승인된 공급자 확인 후 결정한다. 비밀키·실제 메일 자격증명은 저장소에 기록하지 않는다.
5. tester는 핵심 경계와 동시성 테스트를 작성하고, 독립 reviewer가 보안·계약·실패 경로를 검토한다. 필요한 경우 별도 블랙박스 QA를 수행한다. 최초 검증·리뷰 후 지적만 수정하고 해당 수정 여부만 재확인한다. 실제 계약을 공통 API 문서에 동기화한다.
6. 커밋·push·PR은 별도 사용자 요청 범위에서만 한다. 최종 머지는 사람이 한다.

## 완료 기준과 검증

- 정상 발급·확인, 빈 입력·잘못된 형식, 만료 직전/경계, 틀린 번호 5회, 60초 및 시간당 5회 경계, 재발송 시 이전 번호 무효, 인증 성공 재사용 거부, 다른 이메일·목적에 대한 증명 거부를 확인한다.
- 동시 발송·확인에서 제한 우회와 중복 증명 발급이 없는지, Redis 장애·발송 장애에서 성공을 거짓으로 반환하지 않는지 확인한다. 개인정보·코드·증명과 비밀키가 로그에 노출되지 않는지 확인한다.
- `./gradlew test bootJar` 또는 Windows `./gradlew.bat test bootJar`를 대상 서비스에서 실행한다. 격리 Redis·MySQL을 이용한 통합 검증과 실제 메일 공급자 연동 검증을 단위 검사와 구분해 보고한다. 환경·자격증명 미확보 시 해당 검증은 미실행으로 남긴다.
- 기존 계정·자격증명 저장 동작을 보존한다. 가입 API 미구현 상태이므로 발급된 증명의 가입 소비와 전체 회원가입 성공은 이번 검증의 완료로 주장하지 않는다.

## 승인과 진행 상태

- 사용자는 이슈·브랜치 생성 후 발송 구현을 직접 요청했다. 별도의 계획서·이슈 승인 발언은 확인되지 않았다.
- 최초 `gradlew.bat compileJava`, `gradlew.bat test bootJar`는 담당자 보고상 통과했다. 이후 발송 주소 대소문자 보존 지적을 수정했으며 해당 수정 검증은 진행 중이다. 실제 Redis·Brevo 검증 및 최종 리뷰 결과는 메인 확인 전이다.
- 중요한 범위 변경, 필수 미정 정책, 권한·환경 차단, 수정 후 지적 미해결 또는 사용자 중단 요청 시 해당 작업을 중단한다.

- 사용자 요청은 기존 이슈의 다음 단계인 인증번호 확인 구현이다. 확인 API·실패 누적·증명 발급을 구현하되 가입 API와 증명 소비·계정 복구·소셜 인증은 제외한다. 사용자는 커밋 단위 작업을 원했으며 후속 커밋의 구체 승인·푸시·PR은 별도로 확인한다.
- 기존 이슈·브랜치는 사용자의 명시적 지시로 생성됐다. 새 이슈·브랜치를 만들지 않는다. 기존 계획에 다음 단계를 구체화한 이 실행 계획과 미정 정책의 검토가 필요하며 승인·미정 결정은 추정하지 않는다.

### 제안 동작과 필수 결정

1. 요청 ID와 정확히 6자리 ASCII 숫자 코드를 검증한다. ID·목적·만료·최신 요청 여부, 이메일별 잠금과 코드 확인, 실패 횟수 증가 또는 인증 성공 처리를 Redis 원자 연산으로 수행한다. 재발송·동시 확인과 경합하더라도 이전 인증번호가 성공하거나 하나의 번호로 여러 증명이 발급되지 않게 한다.
2. 실패마다 해당 번호의 횟수와 이메일별 누적 실패를 함께 증가시킨다. 5번째 실패는 번호를 즉시 무효화하며 재발송 시에도 누적 상태는 유지한다. 5번째 이후·누적 제한·만료 및 존재하지 않는 ID의 정확한 HTTP 응답을 공통/API 계약과 일치시킨다. 만료된 키가 Redis TTL로 삭제되면 존재하지 않는 ID와 구분할 수 없으므로 404/409 계약을 충족할 안전한 만료 표식이나 계약 변경 여부를 구현 전에 명시한다. 사용자 정책 변경으로 처리하지 않는다.
3. 성공 시 암호학적으로 안전한 고엔트로피 무작위 증명을 반환하고 Redis에는 원문 대신 검증 가능한 해시·이메일 확인값·SIGNUP·발급 절차·만료를 연결해 TTL 600초로 저장하는 방안을 권장한다. 유효한 증명은 후속 가입 절차에 한 번만 연결한다. 응답 유실 후 재확인, Redis 장애 또는 재발송과 성공의 경합 시 증명 중복·재사용·오류 은폐가 없도록 처리한다. 증명 소비 API는 이번에 구현하지 않는다.
4. **사용자 결정:** 같은 이메일에서 최근 1시간 내 인증번호 확인이 총 10회 실패하면 10번째 실패 시점부터 1시간 동안 확인을 제한한다. 재발송해도 누적 실패 횟수를 초기화하지 않으며, 번호별 5회 실패 무효도 유지한다. 성공 시 조기 초기화는 결정되지 않았으므로 1시간 내 실패 기록을 유지하는 방안을 제안한다. 잠금 중 확인은 차단하고 발송은 허용하는 방안은 제안이며 사용자 결정으로 기록하지 않는다. 잠금 만료와 최근 1시간의 실패 기록은 별도로 관리한다.
5. 인증번호 확인 실패가 난 후 발송 단계가 이미 저장한 이메일 확인값을 기반으로 누적 제한을 연결해야 한다. 잘못된 요청 ID에서 이메일을 알 수 없는 경우 무차별 요청 제한의 별도 수단 필요 여부를 검토하고 문서상 확정하지 않은 IP 확인 제한 수치는 임의 지정하지 않는다.

### 순서·변경 범위·검증

1. 메인이 기존 이슈와 브랜치·작업 트리 및 계획을 확인하고, 위 누적 제한의 남은 동작을 결정한다. 확인 구현을 요청한 사용자 발언의 승인 범위를 임의로 확장하지 않는다.
2. implementer는 `emailverification`의 확인 유스케이스·입출력 포트·웹 경로, Redis 어댑터·오류 매핑, 설정 및 서비스 README를 필요한 만큼 수정한다. 발송 경로의 공통 Redis 상태와 동시성 계약도 함께 조정한다. 테스트 담당은 독립적으로 관련 테스트를 작성한다.
3. 정상 확인·번호 5회 실패·재발송 간 누적·잠금 및 해제·만료·없는 ID·잘못된 요청·Redis 장애·동시 성공·재발송 경합·증명 10분 TTL·이메일/목적 연결·재사용 방지를 검증한다. 격리 Redis 실제 Lua 통합 테스트와 단위/웹 테스트를 구분하고 `gradlew.bat test bootJar`를 실행한다. Postman 발송→확인 흐름은 실제 Redis와 임시 MySQL 등 분리된 환경에서 확인하며 실제 Brevo 수신도 구분해 기록한다.
4. 독립 코드·보안 리뷰를 한 번 수행하고 지적 사항 수정 뒤 해당 지적만 재확인한다. 실제 코드와 관련 API·계획 문서를 동기화한다. Postman 사용 예시는 확인 API가 준비된 뒤 실제 응답에 맞춰 기록한다.
5. 미정 정책, 중요 계약 충돌, 접근·실행 환경 차단 또는 해결되지 않은 지적은 완료로 간주하지 않고 메인이 판단한다. 커밋·푸시·PR은 사용자 요청 범위에서만 수행한다.

### 실제 구현 계약과 검증 상태

- `POST /api/auth/email-verifications/{verificationId}/confirm`은 코드 문자열을 받아 200과 `data.emailVerificationToken`, `expiresAt`을 반환한다. 코드 형식은 ASCII 숫자 6자리다. 인증 성공 시 요청은 한 번만 사용되며 이메일 확인값·SIGNUP 목적에 연결된 증명 확인값은 Redis에서 600초 유효하다. 증명 원문은 응답에만 제공하고 저장소에는 HMAC 확인값을 보관한다.
- 유효한 요청에서 번호별 5번째 실패는 번호를 무효화하고 일반적으로 400, 같은 시도가 이메일별 10번째 실패라면 429를 반환한다. 최근 1시간 누적 10번째 실패 시점부터 1시간 확인 제한이며, 재발송과 성공에도 누적 기록을 조기 초기화하지 않는다. 잠금 중 발송은 가능하되 활성 번호 확인은 제한된다.
- 발송 시 상태 표식은 발급 시점부터 24시간 유지한다. 유효시간이 지난 요청의 표식이 `active`면 409, 표식이 없거나 취소·사용 완료된 요청은 404로 처리한다. 이 구분은 표식이 만료·유실되면 유지되지 않는다. Redis 연결 장애·잘못된 키 등은 503으로 처리한다.
- tester 보고: 격리 Redis 통합 5건 및 `gradlew.bat test bootJar` 통과. 실제 메일 수신부터 확인 API까지의 HTTP 연결 검증은 아직 수행하지 않았다. 발송 단계에서 실제 Brevo 수신은 앞선 대화에서 사용자가 확인했다. 정확한 확인 제한 1시간 경계, 실제 서버의 종료·재시작과 증명 소비 동작은 위 검증 결과만으로 보장하지 않는다.
