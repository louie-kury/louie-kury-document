# 계획과 이슈를 사람이 검토하기

<a id="이슈부터-진행하는-개발"></a>
## 일반 기능 개발

“이런 기능 만들어줘”와 같은 일반 기능 구현·수정 요청부터 아래 흐름을 적용한다. 이슈부터 요청했더라도 관련 문서와 검토할 계획이 먼저다. 유효한 기존 계획·승인이 있으면 현재 요청 범위와 일치하는지 확인해 재사용한다.

| 단계 | 담당과 동작 |
| --- | --- |
| 1. 관련 문서 조사 | 메인이 실제 경로·브랜치·미커밋 변경과 대상 서비스를 확인한다. planner는 [읽기 규칙](ROUTING.md#읽기-규칙)에 따라 조사한다. |
| 2. 계획서 작성과 사람 검토 | planner가 [계획서 틀](templates/plan.md)로 사람이 읽을 실행 계획을 저장한다. 메인은 계획서 링크와 범위·문서 근거·검증·후속 게시 범위를 전달하고 사람의 승인을 기다린다. 내부 계획 도구의 목록만으로 대신하지 않는다. |
| 3. 이슈 작성과 사람 검토 | 계획 승인 후 메인이 승인된 계획을 근거로 GitHub 이슈를 작성한다. 계획서·문서 근거·수용 기준·미정 사항을 연결하고 링크를 전달한 뒤 사람의 이슈 승인을 기다린다. |
| 4. 브랜치와 구현·검증 | 이슈 승인 후 Git 컨벤션에 맞는 브랜치를 생성하고 implementer·tester·독립 reviewer를 통해 필요한 구현·검증·리뷰·QA·문서 동기화를 이어간다. 사용자 요청과 계획에 커밋·푸시·PR이 포함됐으면 게시까지 계속하고 PR 링크·검증 결과를 전달한 뒤 대기한다. |
| 5. 팀원 리뷰 요청과 반영 | 사용자가 PR을 먼저 검토하고 팀원에게 리뷰를 요청한다. 리뷰 반영을 맡은 메인은 사용자가 맡긴 범위의 수정·검증·푸시를 수행한다. 댓글·답글·리뷰 재요청은 사용자가 맡긴 범위에서 수행한다. 팀원은 [PR 리뷰 템플릿](templates/pr-review_template.md)을 사용한다. 반영 담당자는 리뷰어용 판정 양식을 사용하지 않는다. |
| 6. 팀원 승인 | 리뷰한 팀원이 최신 변경과 이전 수정 요청의 반영을 확인하고 GitHub에서 **Approve**를 선택한다. |
| 7. 최종 머지 | 사용자가 팀원 승인과 PR 상태를 확인하고 직접 머지한 뒤 완료 대상 이슈의 종료 상태를 확인한다. 열려 있으면 [Git 컨벤션](../convension/GIT_CONVENTIONS.md#pr과-이슈-완료-확인)에 따라 원인과 후속 조치를 확인한다. |

계획 승인은 해당 계획의 이슈 작성을, 이슈 승인은 브랜치 생성과 승인 범위의 구현·검증을 허용한다. 승인 범위의 일상적인 구현 선택과 재작업·역할 전환마다 다시 묻지 않는다. 중요한 요구사항·설계·범위가 달라지면 해당 변경만 다시 합의한다. 사용자 선택·이유·승인을 만들어내지 않는다.

## 대기와 연속 진행

승인 후의 연속 진행과 중단 조건은 [워크플로](WORKFLOW.md#승인-후-이어서-진행하기), 구현 결과의 확인은 [수정 확인과 통과](WORKFLOW.md#수정-확인과-통과)를 따른다. 별도로 요청받은 팀원 리뷰·재리뷰는 해당 요청 범위에서 수행한다.

## 적용 범위

설계·계획·문서·리뷰만 요청받으면 해당 범위만 수행한다. 작은 문구 수정과 상태 답변마다 기능 개발의 전체 파이프라인을 강제하지 않는다. 승인과 후속 지시는 대화로 받고 별도 승인 프로그램이나 긴 승인 문자열은 요구하지 않는다. GitHub Approve와 최종 머지는 사람이 한다. 자동 머지·머지 큐·보호 규칙 우회는 하지 않는다.

이 문서는 세션 진행 규칙이며 문구만으로 실행을 강제하는 프로그램이 아니다. 계획·이슈 승인 대기와 PR 게시 후 대기는 메인이 지킨다. 세션 종료 뒤의 리뷰는 사용자가 다시 작업을 맡겼을 때 이어서 처리한다. 브랜치 보호와 GitHub 필수 조건은 저장소 설정에서 별도로 적용한다.
