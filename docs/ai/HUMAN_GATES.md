# 대화에서 선택하고 확인하기

## 이슈부터 진행하는 개발

| 단계 | 담당과 동작 |
| --- | --- |
| 1. 이슈 작성과 확인 | 사용자가 API 개발 이슈 작성을 요청하면 메인이 해당 PRD·ERD·API 명세를 확인한다. 작업 범위, 문서 근거, 수용 기준, 관련 미정 항목을 담아 GitHub 이슈를 등록한다. 링크를 전달한 뒤 사용자 승인을 기다린다. |
| 2. 계획 작성과 확인 | 사용자가 이슈를 승인하면 메인이 planner에 계획을 맡긴다. 계획에는 구현 범위, 선택과 이유, 검증 기준, PR 게시까지의 범위를 적는다. 메인은 계획을 전달하고 사용자 승인을 기다린다. |
| 3. 구현부터 PR 게시까지 | 사용자가 계획을 승인하면 메인이 implementer에 구현을 맡기고 필요한 테스트·코드 리뷰·QA·문서 동기화를 진행한다. 승인된 범위에서 커밋·푸시·PR 작성까지 이어서 수행한다. PR 링크와 검증 결과를 전달한 뒤 사용자 지시를 기다린다. |
| 4. 팀원 리뷰 요청 | 사용자가 PR의 코드와 설명을 먼저 검토하고 팀원에게 첫 리뷰를 요청한다. 팀원은 [PR 리뷰 템플릿](templates/pr-review_template.md)을 사용한다. |
| 5. 리뷰 반영과 재요청 | 리뷰 반영을 맡은 메인은 수정 요청을 확인하고 담당자에게 수정·관련 재검증을 맡긴다. 같은 PR에 푸시하고 반영 내용·커밋·검증 결과·미반영 사유(해당 시)를 일반 PR 댓글이나 리뷰 스레드 답글로 남긴 뒤 리뷰어에게 다시 검토를 요청한다. 반영 담당자는 리뷰어용 판정 양식을 사용하지 않는다. |
| 6. 팀원 승인 | 리뷰한 팀원이 최신 변경과 이전 수정 요청의 반영을 확인하고 GitHub에서 **Approve**를 선택한다. |
| 7. 최종 머지 | 사용자가 팀원 승인과 PR 상태를 확인하고 직접 머지한 뒤 완료 대상 이슈의 종료 상태를 확인한다. 열려 있으면 [Git 컨벤션](../convension/GIT_CONVENTIONS.md#pr과-이슈-완료-확인)에 따라 원인과 후속 조치를 확인한다. |

이슈 승인은 계획 시작을 허용한다. 계획 승인은 계획에 적힌 범위의 구현과 PR 게시를 허용한다. 계획 단계에서 개발 방향과 이유는 사용자가 정한다. 요구사항이나 중요한 설계가 달라지면 해당 변경을 다시 합의한다. 일반적인 리뷰 반영처럼 이미 합의한 범위의 수정은 재승인 없이 진행한다.

구현과 리뷰 반영에는 [구현·검증 재작업 한도](WORKFLOW.md#구현검증-재작업-한도)를 적용한다. 최초 구현·검증 후 재작업은 최대 2회이며, 3차 검증에도 오류가 남으면 자동 진행을 멈추고 테스트 결과·남은 오류·미검증 범위를 보고한다. 기존 구현·PR 게시 승인을 근거로 한도를 넘기지 않으며, 추가 재작업은 사용자의 명시적 지시를 기다린다.

## 적용 범위

이슈부터 진행하라는 요청에 위 흐름을 적용한다. 설계·문서·리뷰처럼 특정 작업만 요청받으면 해당 작업 범위에서 진행한다. 승인과 후속 지시는 대화로 받는다. 에이전트는 GitHub Approve와 최종 머지를 사람에게 맡기며, 자동 머지·머지 큐·보호 규칙 우회는 사용하지 않는다.

이 문서는 세션의 진행 규칙이다. 이슈·계획 승인 대기와 PR 게시 후 대기는 메인이 지킨다. 세션이 종료된 뒤 접수된 리뷰는 사용자가 작업을 다시 열어 리뷰 반영을 맡길 때 이어서 처리한다. GitHub에서 필요한 승인·리뷰 대화 해결 조건은 저장소의 브랜치 보호 또는 규칙 세트에서 별도로 적용한다.
