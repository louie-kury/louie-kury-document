# 작업 이름 — 실행 계획서

- 상태: 제안 / 계획 승인 / 이슈 승인 / 실행 중 / 완료 중 현재 상태
- 대상 저장소·브랜치·기존 변경:
- 작성일과 계획 승인 근거:
- 이슈 링크와 이슈 승인 근거: 계획 승인 뒤 작성하며, 아직 없으면 미작성으로 표시

## 목적과 범위

- 사용자가 기대하는 결과:
- 이번에 변경할 것과 제외할 것:
- 기존 유효한 설계·명세: 있으면 연결하되 실행 계획을 생략하지 않는다.

## 조사한 문서와 확인한 사실

| 자료·경로·절 | 이번 작업에 적용되는 사실·제약 | 계획에 반영할 내용 |
| --- | --- | --- |
| PRD 기능·정책 | 기능 ID·수용 기준·미정 사항 | |
| ERD | 관련 엔티티·참조 관계·필수값·유일성 등 제약과 저장소 | |
| API 공통 계약·도메인 | 입력·출력·오류·권한 | |
| 컨벤션·대상 서비스 설정 | 구조·기술·검증 명령 | |

관련 자료를 모두 조사한다. 작업에 해당하지 않는 자료는 이유를 적고, 자료가 없거나 충돌하면 그 사실을 적는다. 문서에 있는 답을 사람에게 다시 묻지 않는다.

## 제안하는 동작과 선택

- 현재 동작 → 변경 후 동작:
- 사용자 입력 → 처리 → 데이터 저장·출력:
- 중요한 대안·권장안·이유:
- 이미 사용자가 정한 내용과 AI가 제안한 내용:
- 문서로 해결되지 않은 필수 질문:

사용자가 말하지 않은 선택 이유나 승인은 만들어내지 않는다. 일반 작업에서는 근거 있는 권장안을 먼저 제시할 수 있다. 학습 모드는 사용자가 명시적으로 요청한 경우에만 적용한다.

## 진행 순서와 변경 파일

1. 사람이 이 계획을 검토하고 승인한다.
2. 승인된 계획으로 이슈를 작성하고 사람이 이슈를 검토·승인한다.
3. 이슈 승인 뒤 Git 컨벤션에 맞는 브랜치를 생성한다.
4. 변경 파일·담당 역할·구현 순서:
5. 검증·독립 리뷰·필요한 QA·문서 동기화:
6. 커밋·푸시·PR 게시 범위: 사용자 요청과 계획에 포함된 작업만 명시

## 완료 기준과 검증

- 정상·경계·빈 입력·실패 조건의 기대 결과:
- 보존할 기존 동작:
- 실행할 명령과 환경, 실제 서버·DB·외부 연동 확인 여부:
- 실행할 수 없는 검증과 남은 위험:

## 승인과 진행 상태

- 계획 승인·이슈 승인: 실제 사용자 발언·대상 범위를 기록하며 미승인은 구분한다.
- 승인 후 메인이 이어서 수행할 일:
- 중단 조건: 두 승인 대기, 중요한 범위·설계 변경, 필수 미정 정책, 권한·환경 차단, 재작업 한도, 사용자 중단 요청
- 재작업 횟수와 남은 일:

담당자 반환과 중간 보고 때문에 다시 승인받지 않는다. 같은 범위의 기존 명시적 실행 지시는 재확인하지 않는다. PR 게시까지 맡긴 작업은 게시 후 사람이 검토하도록 대기한다. 최종 머지는 사람이 한다.
