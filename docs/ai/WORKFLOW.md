# 메인과 네 명의 담당자

다섯 역할이다. **메인은 현재 세션**이므로 별도 서브 에이전트 파일을 만들지 않는다. `.codex/agents/`에는 아래 네 담당자만 등록한다.

| 담당 | 하는 일 | 수정할 수 있는 것 |
| --- | --- | --- |
| 메인 오케스트레이터 | 사용자 대화, 명령/범위 배정, 결과 확인, 단계 통과·재작업 판단 | 사용자가 허용한 설정·통합 작업. 다른 담당의 범위를 몰래 대신 처리하지 않는다 |
| planner | 처음 설계, 마지막 문서 동기화 | 지정된 설계·API·안내 문서 |
| implementer | 합의한 설계 구현·버그 수정 | 실제 구현 코드와 허용된 구현 설정. 테스트 수정 금지 |
| tester | 기대 결과에 맞춘 테스트 작성·실행 | 테스트 코드·전용 fixture와 허용된 테스트 설정. 실제 구현 수정 금지 |
| reviewer | 코드 리뷰 또는 별도 호출의 블랙박스 QA | 파일 수정 없이 읽기·안전한 실행 결과 보고 |

## 단계 선택과 순서

일반 기능 개발은 [휴먼게이트](HUMAN_GATES.md#일반-기능-개발)의 **관련 문서 조사 → planner 계획서 → 사람의 계획 승인 → 이슈 작성 → 사람의 이슈 승인 → 브랜치 생성 → 구현·검증**을 따른다. 계획 승인 전에 이슈를 만들거나 이슈 승인 전에 브랜치·구현을 시작하지 않는다. 설계·리뷰·문서만 요청받으면 요청 범위를 유지한다.

- **처음 planner:** 모든 기능 구현·수정에서 [계획서 틀](templates/plan.md)로 실행 계획서를 작성한다. 유효한 기능 설계는 재사용하되 실행 계획을 생략하지 않는다. 관련 PRD·ERD·API·정책·컨벤션을 모두 조사하고 근거 경로·절, ERD 엔티티·관계·제약과 작업 순서·완료 기준을 기록한다. 자료에 있는 답을 다시 묻지 않고 문서에 없는 필수 정책이나 충돌만 근거와 함께 질문한다. 일반 계획에 VibeWise를 자동 적용하지 않고 사용자가 학습 모드를 명시적으로 요청한 경우에만 적용한다.
- **두 번의 사람 검토:** 메인이 계획서를 전달하고 승인받은 뒤 그 계획으로 이슈를 작성한다. 이슈 링크와 범위를 전달하고 승인받으면 브랜치를 생성한다. [Git 컨벤션](../convension/GIT_CONVENTIONS.md)을 따른다. 이미 받은 명시적 승인·실행 지시는 같은 범위에 다시 요구하지 않는다. 일반 기능 요청 자체를 두 게이트의 승인으로 추정하지 않는다.
- **구현과 검사:** 코드 변경은 implementer에 배정한다. 테스트 작성이나 실행이 필요하면 tester에 관련 검사만 배정한다. 순수 문구 변경은 해당 내용과 링크를 확인한다. tester는 구현 버그의 재현·기대/실제 결과를 메인에 보낸다. 메인은 원인에 따라 구현 또는 테스트 담당에게 지적 사항 수정을 배정하고, [수정 확인과 통과](#수정-확인과-통과) 기준을 따른다.
- **코드 리뷰와 QA:** 코드 리뷰 요청이나 동작·권한·데이터·외부 계약에 영향을 주는 변경은 코드 리뷰 대상으로 삼는다. 실제 화면이나 API의 외부 동작 검증이 요청됐거나 완료 기준에 포함되면 QA를 선택한다. 두 작업이 모두 필요하면 새 reviewer를 각각 호출한다. QA에는 명세·API 계약·사용자 흐름·실행 주소를 전달한다. 필요한 실행 환경이 없으면 QA 결과에 실행 불가를 기록한다.
- **마지막 planner:** 게시할 변경이 API·설계·실행 안내에 영향을 주면 docs-sync를 배정한다. planner는 최종 구현과 선택한 단계의 결과를 받아 관련 문서를 실제에 맞춘다. 계약이나 요구사항의 의미가 달라지면 메인에게 돌려보낸다.
- **메인 최종 확인:** 변경 파일 소유권, 검사/리뷰/QA 결과와 미실행 범위, 문서의 실제 일치를 확인한다. 지적 사항을 수정했다면 해당 수정 여부만 확인하고 전체 검증·자체 리뷰를 다시 시작하지 않는다. 계약이나 요구사항의 의미가 달라졌다면 해당 범위 변경을 사용자와 합의한다. 실행 불가 단계는 사용자에게 알려 판단받고, 메인이 스스로 성공 처리하지 않는다.

## 승인 후 이어서 진행하기

이슈 승인 뒤에는 메인이 필요한 역할을 배정하고 결과를 확인해 다음 단계로 계속 이어간다. 서브 에이전트의 완료 보고·질문 반환은 메인에게 돌아오는 결과이며 그 자체로 사용자 승인 대기나 채팅 종료가 아니다. 승인 범위의 구현·검증·독립 리뷰·필요한 QA·문서 동기화·허용된 재작업에 반복 승인을 요구하지 않는다. 커밋·푸시·PR은 사용자 요청과 계획에 포함된 범위에서 이어서 실행하고 PR 게시 후 대기한다.

사람을 기다리는 시점은 계획 승인, 이슈 승인, 중요한 요구사항·설계·범위 변경, 문서로 해결되지 않는 필수 정책, 권한·실행 환경의 차단, 수정 확인 후 남은 지적 사항, 사용자의 중단 요청이다. 차단과 무관하게 가능한 작업은 계속하되 승인 전 다음 게이트를 넘지 않는다. 선택한 필수 검증이 실행 불가하면 성공 처리하지 않고 결과와 필요한 조치를 보고한다. 단순 진행 보고·담당 교체는 중단 조건이 아니다.

사용자가 제시된 변경에 대해 “수정하고 PR 올리고 대기”처럼 후속 실행 범위를 명시했다면 그 범위의 기존 권한을 재확인하지 않는다. 이를 일반 기능 요청의 계획·이슈 승인 생략 규칙으로 확대하지 않는다. 설계·리뷰 등으로 잠근 범위나 최종 머지를 이 지시로 넓히지 않는다.

## 컨텍스트·검증 비용 관리

읽기·위임·검증의 반복 비용을 줄인다. 최초에 필요한 테스트·독립 리뷰·QA는 수행하고, 지적 사항 수정 후에는 수정 여부만 확인한다.

- **읽기:** [ROUTING](ROUTING.md)의 작업 행에서 관련 문서·절을 모두 찾는다. PRD·ERD·API·과거 검증 자료 전체를 매번 불러오지 않되 읽기 비용 절감을 이유로 관련 ERD·API·정책·컨벤션을 생략하지 않는다. 파일 목록과 `rg`로 근거를 조사하고 부족할 때 범위를 넓힌다. 같은 세션에서 확인한 내용은 변경되지 않았으면 다시 읽지 않는다.
- **위임:** 현재 작업 하나의 목적·허용 경로·완료 기준·문서 절·비교 기준·직전 변경·실패 요약을 전달한다. 독립 서브 작업은 가능하면 전체 대화 상속 대신 이 정보로 시작한다. 원문 diff·로그·명세를 메인과 모든 담당자에게 반복 복사하지 않고 경로·SHA·필요한 줄을 전달한다. 전체 대화가 판단에 필요한 경우에만 상속한다.
- **담당 유지:** 같은 작업의 implementer·tester는 후속 지시로 재사용한다. 재개가 불가능하면 이전 변경·검증·남은 일을 짧게 전달한다. 무관한 작업·설계 대전환·컨텍스트 과다 시 새로 시작한다. 최초 독립 코드 리뷰·QA는 각각 새 reviewer를 사용한다. 수정 후 확인에는 기존 지적 목록과 변경 근거를 전달하며, 세션을 바꿔 전체 검증·자체 리뷰를 다시 시작하지 않는다.
- **스킬:** 역할 파일과 프로젝트 전용 스킬이 정한 절차를 사용한다. 같은 계획·리뷰·검증을 수행하는 범용 스킬이나 별도 검토 체인을 겹쳐 실행하지 않는다. 추가 분석은 현재 작업에서 해결되지 않은 문제에 한정한다.
- **리뷰:** 처음에는 실제 PR 대상 브랜치와 최신 head의 비교 기준, 변경 파일 목록·diff, 관련 계약부터 확인한다. 결함 판단에 필요한 호출부·보호 장치만 따라 읽는다. 자체 리뷰는 한 차례 수행한다. 이후에는 이전 지적과 이후 변경분을 대조해 해당 지적이 해결됐는지만 확인하고 전체 자체 리뷰를 반복하지 않는다. 비교 근거가 불명확하면 확인 불가로 보고하며 통과로 처리하지 않는다. 메인은 결과와 근거를 확인하되 같은 리뷰를 별도로 반복하지 않는다. 사람이 맡긴 팀원 PR 리뷰·재리뷰는 요청받은 범위에서 수행한다.
- **검증:** 먼저 기존 결과·CI의 명령·대상 SHA·검증 범위·환경을 확인한다. 현재 변경을 포함하고 환경·계약이 유효한 성공 결과는 재사용한다. CI가 PR 병합 결과를 검사했다면 그 head/base도 확인한다. 단순히 PR 본문에 성공이라고 적혀 있거나 관련 SHA가 다르면 재사용 근거로 삼지 않는다. 최초 검증에서는 필수 검사가 없거나 유효한 결과가 없는 범위의 검사를 실행한다. 문서 변경은 내용·링크를 확인하고 실행 스크립트·역할 설정·빌드 설정 변경은 필요한 설정 검사와 회귀 검증을 수행한다. 지적 사항 수정 후에는 수정 내용 대조나 해당 실패 사례의 확인 등 해결 여부를 판단할 최소 확인만 수행하며 전체 검증을 반복하지 않는다. 최초 검증 결과와 수정 확인 결과는 구분해 보고한다.
- **결과:** 담당자는 변경 파일·판정·명령·결과·근거 위치·남은 위험만 반환한다. 로그는 실패를 설명하는 부분과 전체 로그 위치를 전달한다. 긴 작업의 중간 체크포인트는 중요한 결정·실패·단계 전환에 남기고, 매 도구 호출마다 인계 파일을 만들지 않는다.

절감 효과는 실측 전 수치로 단정하지 않는다. 비교할 때는 비슷한 작업의 토큰 사용량(제공되는 경우), 신규/재사용 담당자 수, 중복 읽기·검증 여부와 결함 누락·재작업을 함께 본다.

하네스 절차를 바꾸기 전 기준 작업 1건과 적용 후 비슷한 규모의 작업 1건을 선택한다. 작업자가 각 기능 작업 시작·종료 시점에 보이는 5시간·주간 사용률과 남은 컨텍스트를 전달하면 메인이 [PR 템플릿](../../.github/pull_request_template.md)의 사용량 항목에 기록한다. 사용률 집계가 초기화됐거나 컨텍스트 측정 세션이 달라졌으면 비교에 미치는 영향을 함께 적는다.

메인은 역할별 실제 호출 수와 코드 리뷰 라운드 수를 센다. 같은 담당자에게 다시 위임한 호출도 포함하고, 같은 라운드에서 기존 지적의 수정 여부를 확인하는 절차는 라운드를 추가하지 않는다. 호출이 없으면 0으로 기록하고, 확보하지 못한 값은 `측정 대기`로 남긴다. 대화 전문이나 개인정보는 남기지 않는다.

## 수정 확인과 통과

작업 흐름은 **구현 → 검증(자체 리뷰) → 지적 사항 수정 → 수정 여부 확인 → 통과**로 진행한다. 최초 구현 후 변경 영향에 맞는 검증과 자체 리뷰를 한 차례 수행한다. 선택한 테스트·코드 리뷰·QA의 결과와 지적 사항을 모으고, 지적이 없으면 바로 통과한다.

지적 사항이 있으면 메인이 원인에 따라 구현·테스트·문서 담당에게 수정을 배정한다. 수정 후에는 기존 지적 목록과 변경 내용을 대조하고, 필요한 경우 해당 실패 사례만 확인하여 각 지적의 해결 여부를 판단한다. 전체 테스트·검증이나 전체 자체 리뷰를 다시 돌리지 않고, 담당자·검증 종류·세션을 바꿔 같은 검토를 반복하지 않는다. 수정 확인은 새 검증 차수를 시작하는 단계가 아니다. 인계에는 지적 사항별 수정 내용·확인 근거·남은 항목을 남긴다.

지적 사항이 해결됐음을 확인하면 통과하고 승인된 다음 단계로 이어간다. 확인 후에도 미해결 지적이 있거나 필수 검증·수정 확인을 실행할 수 없다면 통과나 완료로 보고하지 않는다. 남은 문제·실제 확인 결과·미검증 범위를 보고하고 사용자 지시를 기다리며, 자동으로 추가 수정·전체 검증·자체 리뷰 반복을 시작하지 않는다. 내부 자체 리뷰 통과는 사람이 수행하는 GitHub Approve나 최종 머지를 대신하지 않는다.

## 설계 결정 기록

합의한 주요 설계 결정은 ADR(Architecture Decision Record)로 남긴다. 결정 하나당 배경, 선택과 이유, 영향을 짧게 적는다.

- 한 서비스에만 적용되는 결정은 해당 서비스 레포의 `docs/adr/`에 기록한다. 예를 들어 상품 서비스의 내부 데이터 모델을 바꾸면 관련 코드와 ADR을 상품 레포의 같은 PR에 포함할 수 있다.
- 여러 서비스가 함께 따르는 결정은 공통 문서 레포의 `docs/adr/`에 기록한다. 서비스 경계, 서비스 간 API·이벤트 계약, 공통 하네스 배치가 이에 해당한다.

## 서비스 작업 경로

프론트엔드와 백엔드는 이 공통 문서 레포에서 Codex 채팅을 시작한다. 경로는 공통 문서 레포 루트를 기준으로 계산하고, 사용자가 작업 경로를 지정하면 그 경로를 우선한다.

- 프론트엔드 작업은 기본적으로 형제 폴더에 클론한 `../louie-kury-front/`에서 진행한다. 최초 프로젝트 초기화도 이 프론트 레포 안에서 진행한다. 해당 클론을 찾지 못하면 실제 클론 경로를 확인한다.

- 새 백엔드 서비스 생성 요청은 서비스 이름으로 형제 폴더를 정한다. 예를 들어 `product-service`를 만들어 달라는 요청이면 `../product-service/`에 프로젝트를 초기화한다. 대상 경로에 기존 파일이 있으면 상태와 용도를 먼저 확인한다.
- 기존 백엔드 기능의 구현·수정 요청은 해당 서비스를 찾아 그 폴더에서 진행한다. 요청과 실제 파일로 대상 서비스를 하나로 특정할 수 없으면 사용자에게 대상 서비스나 경로를 확인한다.
- 새 서비스 프로젝트를 초기화할 때 [서비스 레포용 AGENTS.md 템플릿](templates/service-agents.md)을 적용하고 공통 문서 경로를 실제 클론 위치에 맞춘다. 구현과 빌드·테스트는 대상 레포에서 실행한다.
- 서비스 경로가 Codex 작업 공간 밖이면 해당 경로를 작업 공간에 추가해야 할 수 있다. 아직 없는 폴더를 만들 수 있도록 서비스 경로의 상위 폴더가 쓰기 가능한지 확인한다.

## 짧게 위임하기

메인은 작업 목적·사용자 결정·허용 파일·완료 기준·실행 명령/환경·단계나 모드를 전달한다. 공통 문서와 대상 레포의 경로를 각각 명시하고, 역할에 필요한 문서의 절·기능 ID·근거 위치를 지정한다. 에이전트는 적용되는 저장소 지침과 배정 자료를 확인하고, 추가 근거가 필요하면 관련 절만 찾는다. 단계 판정과 다음 명령의 배정은 메인이 맡는다.

planner의 질문은 메인이 먼저 관련 문서·기존 결정으로 해결 가능한지 확인하고 해결되지 않는 필수 사항만 사람에게 전달해 답을 되돌려준다. 서브 에이전트가 사용자의 답을 만들어내거나 승인 없이 구현하지 않는다. 설계 질문을 위해 별도 에이전트를 추가하지 않는다. 작성 담당자가 같은 파일을 동시에 수정하지 않게 한다.

설계·문서·리뷰만 요청받으면 해당 단계만 수행한다. 기능 개발은 계획 승인 후 이슈를 작성하고 제한된 문서·리뷰 요청에 이슈나 전체 개발 단계를 붙이지 않는다. 긴 승인 문자열은 사용하지 않는다. 메인은 [대화에서 확인](HUMAN_GATES.md)하고 중요한 선택과 진행 단계는 `$project-handoff`에 저장한다.

## 실제 권한의 한계

이 표는 담당별 작업 규칙이다. 역할 파일은 부모 세션의 도구·권한을 상속하며 파일별 OS 접근 차단을 만들지 않는다. 메인이 diff/실행 결과로 위반을 확인하고 중단한다. [OpenAI 공식 에이전트 설정](https://learn.chatgpt.com/docs/agent-configuration/subagents)을 따른다. 모델·권한 상승·추가 훅은 설정하지 않는다.
