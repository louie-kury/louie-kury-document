# 루이쿠리 프론트엔드 코드 컨벤션

## 1. 적용 범위

- 프론트엔드 소스와 테스트의 신규 작성·수정·리뷰에 적용한다. 기존 파일을 수정할 때는 변경에 필요한 범위에 적용한다. 생성 코드를 바꿔야 하면 생성 원본이나 설정을 수정한다.
- 제품 동작은 [PRD](../prd.md)의 기능 요구사항과 수용 기준을 따르고, 서버 연동은 [API 명세](../api/README.md)의 관련 계약을 확인한다. 미정 정책이 구현에 영향을 주면 해당 결정을 먼저 확인한다.
- **필수**는 적용할 규칙, **금지**는 피해야 할 구현, **권장**은 특별한 사유가 없을 때 따를 기본값이다. 기존 호환성이나 외부 계약 때문에 예외가 필요하면 적용 범위와 이유를 리뷰에 남긴다.
- 프론트엔드 기술 스택은 미정이다. 예제는 HTML과 JavaScript를 사용한다. 언어·프레임워크·빌드·테스트 도구별 설정은 기술을 정할 때 프로젝트 설정과 이 문서에 반영한다.

## 2. 파일과 코드 서식

- **필수** 텍스트 파일은 UTF-8과 LF를 사용하고 끝에 개행 하나를 둔다. 포맷터가 설정된 프로젝트에서는 팀 설정을 적용한다.
- **권장** 초기 예제는 스페이스 2칸으로 들여쓴다. 인자나 객체 속성이 한 줄에 읽기 어렵게 늘어나면 여러 줄로 배치한다. 긴 조건은 의미를 드러내는 이름으로 분리한다.
- **필수** 사용하지 않는 import와 변수를 제거한다. 모듈 내부에서만 쓰는 함수는 내부에 두고, 호출자가 사용하는 함수만 내보낸다.
- **권장** 외부 의존성과 프로젝트 내부 import를 구분한다. 부수 효과가 있는 import는 실행 순서를 확인한 뒤 이동한다.

## 3. 이름 짓기

| 대상 | 기본 표기 | 예시 |
| --- | --- | --- |
| 기능 폴더 | 영문 소문자와 하이픈 | `pet-profile/` |
| 화면 컴포넌트·타입 이름 | `PascalCase` | `PetList`, `PetListItem` |
| 함수·변수 | `camelCase` | `fetchPets()`, `selectedPetId` |
| 참·거짓 값 | `is`, `has`, `can` 등 의미가 드러나는 이름 | `isSubmitting`, `hasPets`, `canEdit` |
| 고정된 한도·설정 상수 | `UPPER_SNAKE_CASE` | `REQUEST_TIMEOUT_MS` |

- **권장** 함수는 수행하는 동작으로 이름을 짓는다. 사용자 이벤트 처리 함수에는 `handleSubmit`, 외부에서 전달하는 콜백에는 `onSubmit`처럼 역할을 표현한다.
- **권장** 같은 개념에 같은 도메인 용어를 사용한다. 예를 들어 수의사는 `veterinarian`, 수의사 식별자는 `veterinarianId`로 적는다. 시간과 수량의 단위가 타입에서 드러나지 않으면 이름에 명시한다.
- **필수** API 필드명과 프레임워크가 요구하는 파일명은 해당 계약과 규칙을 따른다.

## 4. 폴더 구조와 책임

관련 화면·요청·테스트는 기능 가까이에 둔다. 아래는 배치 예시다. 실제 경로는 선택한 프레임워크의 라우팅 구조와 레포 설정에 맞춘다.

```text
src/
├── features/
│   └── pets/
│       ├── pet-list.js
│       ├── pet-api.js
│       └── pet-list.test.js
└── shared/
    ├── api/
    └── ui/
```

- **필수** 화면은 사용자 입력과 표시를 담당하고, HTTP 요청과 공통 응답 처리는 API 모듈에 둔다. 레포에 공통 요청 함수가 있으면 재사용한다.
- **권장** 여러 기능에서 사용하는 UI와 요청 기반 코드는 공통 폴더에 둔다. 공통 모듈은 개별 기능 내부 파일에 의존하지 않게 구성한다.
- **권장** 컴포넌트는 화면에서 맡은 역할을 이름으로 설명할 수 있을 때 분리한다. 동일한 화면 흐름을 이해하려고 여러 파일을 오가야 한다면 관련 코드를 가까이 둔다.

## 5. 상태와 화면 표시

- **필수** 화면에서 수정하는 값은 담당 위치를 한 곳으로 정한다. 이미 가진 값으로 계산할 수 있는 값은 원본을 기준으로 구한다.
- **권장** 한 화면의 입력값은 그 화면 가까이에서 관리한다. 화면 간 공유나 새로고침 후 유지가 필요할 때 URL, 공통 상태 또는 서버 저장을 검토한다.
- **필수** 조회 화면은 최초 로딩, 데이터가 있는 성공, 빈 결과, 실패를 구분한다. 기존 데이터를 표시한 채 갱신한다면 갱신 결과가 화면에 어떻게 반영되는지 확인한다.
- **권장** 서로 배타적인 상태는 상태값 하나로 표현한다. 예를 들어 조회 결과를 `loading`, `success`, `error`로 구분하고, `success`일 때 목록 길이로 빈 화면을 판단한다.

**권장 · 목록 상태에서 화면 유형 계산**

```js
function getPetListView(petList) {
  if (petList.status !== 'success') {
    return petList.status;
  }

  return petList.items.length === 0 ? 'empty' : 'list';
}
```

**피할 예 · 목록과 빈 상태를 따로 저장**

```js
let pets = [];
let isEmpty = true;

pets = [{ petId: 'pet-1', name: '루이' }];
// 목록이 변경됐는데 isEmpty는 true로 남는다.
```

## 6. API와 외부 데이터

- **필수** 요청 메서드·경로·필드·오류 코드는 계약에 맞춘다. 필드 생략, `null`, 빈 배열은 계약에 정의된 의미대로 처리한다.
- **필수** HTTP 실패와 네트워크 실패를 처리한다. 브라우저 `fetch`를 직접 쓰는 경우에도 응답 상태를 확인한다. 공통 클라이언트가 처리하는 응답 포맷·인증·오류 변환은 그 모듈을 사용한다.
- **권장** 입력값이나 API 응답을 화면에 맞게 변환하는 위치를 한 곳으로 모은다. 외부 데이터의 형식이 달라질 수 있는 경계는 실제 값으로 확인한다.
- **필수** 검색이나 필터 변경으로 요청이 겹칠 때 이전 요청의 늦은 응답이 현재 화면을 덮어쓰지 않게 한다. 사용 중인 요청 도구의 취소나 최신 요청 확인 기능을 사용한다.

## 7. 폼과 오류 처리

- **필수** 필수 입력과 형식 오류는 관련 필드 근처에 알린다. 서버에서 거절한 경우에도 사용자가 원인을 이해하고 수정할 수 있게 안내한다.
- **필수** 같은 요청이 반복되면 데이터가 중복 생성되거나 결제가 반복되는 흐름에서는 요청이 진행 중인 동안 중복 제출을 막는다. 재시도는 API 계약이 허용하는 경우에 제공한다.
- **권장** 저장에 실패하면 사용자가 입력한 값을 유지한다. 성공 여부를 화면에서 확인할 수 있게 하고 화면 이동이나 목록 갱신은 계약과 수용 기준을 따른다.

## 8. HTML·스타일·접근성

- **필수** 화면 이동은 링크, 실행은 버튼, 입력은 해당 폼 요소로 구현한다. 레이블, 키보드 이동과 실행, 포커스 표시를 확인한다. [W3C 폼 레이블 안내](https://www.w3.org/WAI/tutorials/forms/labels/)
- **필수** 입력 오류나 필수 상태는 색과 함께 텍스트로 알린다. 의미 있는 이미지에는 내용을 설명하는 대체 텍스트를 제공한다.
- **권장** 프로젝트에 정의된 색상·간격·타이포그래피 값을 재사용하고, 화면 전용 스타일의 적용 범위를 제한한다. 작은 화면과 긴 데이터에서도 주요 동작이 가려지지 않는지 확인한다.

**허용 · 입력과 레이블 연결**

```html
<label for="pet-name">반려동물 이름</label>
<input id="pet-name" name="name" required />
<button type="submit">저장</button>
```

**위반 · 레이블을 플레이스홀더로 대체**

```html
<input name="name" placeholder="반려동물 이름" />
```

## 9. 인증과 설정

- **금지** 인증 토큰이나 개인정보를 URL, 콘솔 로그, 오류 알림에 노출한다. 인증 정보 저장과 세션 처리는 팀이 합의한 인증 방식에 따른다.
- **필수** 브라우저에 전달되는 설정과 환경 변수는 공개될 수 있는 값만 사용한다. 화면에서 버튼을 숨기더라도 실제 접근 제어는 서버의 인증·인가 결과를 따른다.
- **필수** 서버와 사용자 입력으로 받은 문자열을 기본적으로 텍스트로 렌더링한다. HTML 렌더링이 필요한 기능은 프로젝트가 정한 정제 방식을 적용한다.

## 10. 테스트와 리뷰

- **필수** 변경한 기능을 PRD의 수용 기준과 API 계약으로 검증한다. 관련된 정상 흐름, 입력 경계, 빈 결과, 오류 후 복구를 필요한 만큼 개별 사례로 확인한다.
- **권장** 컴포넌트 테스트는 사용자가 보는 이름과 조작하는 요소를 기준으로 작성한다. 예를 들어 저장 버튼을 누른 뒤 성공 안내가 나타나는지 확인한다. [Testing Library 검증 원칙](https://testing-library.com/docs/guiding-principles/)
- **필수** 대상 레포에 설정된 포맷·린트·타입 검사·테스트·빌드 중 변경에 관련된 검사를 실행한다. 브라우저에서 확인한 범위와 API 모킹 또는 실제 서버를 사용한 범위를 구분해 기록한다.
